# Operations

## GitHub and repository trust

Register each repository centrally under `ingress.repositories` with its exact
GARM repository ID and a file containing the webhook secret value. A GitHub
App's configured webhook secret may be shared by every installed repository;
separate repository hooks may use different values. For each delivery, the
GitHub hook/App secret, the configured file contents, and the matching GARM
repository entity's webhook secret must have the same value. Outrider checks
the signature, then forwards the original signed body and signature to GARM
without re-signing it. GARM verifies that signature with the repository
entity's secret ([GARM v0.2.1 source](https://github.com/cloudbase/garm/blob/154638445c3949c1958b01812f69d9a1e4d82684/runner/runner.go#L887-L895)).
Outrider sets GARM's hook target header to `repository`, matching its pool
registration scope. GitHub App deliveries use `integration`, which GARM rejects.
The original headers remain in the inbox; signed body bytes stay unchanged.
Only jobs carrying a complete Outrider routing label are relayed to GARM.
Other authenticated deliveries are acknowledged locally. Run-completion events
still persist terminal barriers and drive Outrider pool cleanup locally.
Configure a separate GARM webhook for GARM-native jobs outside Outrider.
The case-insensitive `outrider` label prefix is reserved; malformed request
labels receive an admission check instead of being silently ignored.
Set `allow_forks: true` only when an administrator has explicitly approved
fork workflows; the default is denial. Keep the secret file readable only by
the daemon account.

Subscribe the webhook to both signed `workflow_job` and `workflow_run` events.
`workflow_job` queued events request runner admission. Waiting events report
environment approval and never admit a runner; after approval, GitHub can
deliver a later queued event. Outrider checks the authenticated job's current
status, so delayed queued events do not create pools or get relayed as new
admissions. `workflow_run` with action `completed` provides run completion and
cancellation observations used to close out terminal state and interruption
recovery. Deliver completed workflow runs, including those whose conclusion is
`cancelled`, as well as queued job events; filtering to job starts leaves
recovery state incomplete.

Jobs from `push`, `merge_group`, and centrally permitted pull request events
are supported, along with `workflow_dispatch`, `schedule`, `release`, and
`repository_dispatch`. Outrider reads the authenticated run attempt and uses
its exact `head_sha` to fetch `.outrider.toml`; branch and tag names are never
resolved to a moving tip. The repository's configured fork policy still
applies to pull request events, and `pull_request_target` remains denied unless
an administrator explicitly enables forks.
Give the GitHub App Actions read access for workflow runs and jobs, Contents
read access for repository configuration and commit provenance, and Checks
write access for rejection/status reporting. Enable Actions write only when
bounded reruns are enabled. GARM's GitHub App and repository-scoped runner
registration follow the GARM deployment's own configuration and permissions.

Configure the workflow with exactly one complete Outrider request label, such
as the value generated by `outrider label`; do not split it into multiple
labels or author internal GARM routing labels. Outrider creates the repository
pool and relays the original signed webhook. It freezes repository config from
the exact workflow commit together with the GARM pool snapshot before routing.
The request token identifies repository, run, attempt, profile, and permitted
overrides. It is not a secret. Authorization comes from signature validation,
GitHub job/run provenance, repository registration, and central policy.

For the base profile, put the complete label expression directly in
`runs-on`; a preparation job is not required:

```yaml
jobs:
  build:
    runs-on: "outrider:v1:${{ github.repository_id }}:${{ github.run_id }}:${{ github.run_attempt }}:default"
    steps:
      - uses: actions/checkout@v4
      - run: ./build.sh
```

To generate a concrete token with an allowed override, use the CLI and keep
its full output as the single label:

```sh
outrider label --repository-id 7 --run-id 8 --attempt 1 --profile default --override vcpu=4
```

This prints `outrider:v1:7:8:1:default:vcpu=4`. The parser accepts that
canonical token with:

```sh
outrider label --token outrider:v1:7:8:1:default:vcpu=4
```

Use the exact repository config path `.outrider.toml`. Central configuration
owns provider credentials, hard limits, purchasing policy, and allowed clouds;
the repository file selects a profile and permitted selector lists only.

## Explain a live selection

GCP can omit architecture from older machine types such as E2 and N2. For those
exact machine names, administrators may set `machine_facts.NAME.architecture`
to `amd64` or `arm64`, with the evidence recorded in that entry's required
`source`. Verify it against the provider's machine-family documentation.
Native and attested values must agree when both exist; missing both excludes
the machine. The image architecture is checked separately. This fact belongs
in central catalog configuration and cannot be supplied by repository/job overrides.

Run `outrider explain` from a host with access to the configured daemon. With no
selector it analyzes the current central `default` profile; `--profile NAME`
selects another current central profile. `--snapshot ID` analyzes the exact
retained repository/job snapshot, including its frozen profile and catalog pins,
after checking snapshot eligibility and current hard limits.

```sh
outrider explain --config /etc/outrider/central.toml --profile linux-large
outrider explain --config /etc/outrider/central.toml --snapshot SNAPSHOT_ID
```

Explain sends an authenticated loopback request to the daemon. It performs the
same scoped catalog, quote, history, freshness, and policy analysis as Create,
within the smaller of the allocation and bootstrap budgets, minus the timeout
margin. It does not reserve an allocation, consume a cap, create a pool, invoke
a provider child, post a check, or submit a rerun. Read-only cloud SDK requests
and journal history reads still occur. The JSON report includes normalized
requirements and snapshot identity when a retained snapshot was selected,
queried catalog scope, observed adapter exclusions, candidate order and
rejection reasons, policy fallback attempts, price components and ages,
history coverage, and a readable
`financial_price_scope` for each constructed offer. It is bounded and marks
truncated lists explicitly. Empty or rejected analyses retain their policy and
catalog diagnostics; they do not imply that unqueried machine shapes were
evaluated. The report omits provider configuration, credential paths/values,
child stderr, bootstrap labels, and opaque provider pins.

Collect native VM, disk and allocated IP metadata through the same daemon:

```sh
outrider inventory --config /etc/outrider/central.toml
```

Inventory uses each connected current or retained catalog's verified credentials.
It includes untagged resources and resources tagged for another controller,
classifying ownership without exporting tag values or bootstrap data. AWS uses
the configured region, Azure the subscription, and GCP the configured zone for
VMs/disks and that zone's region for allocated addresses, including internal
addresses. Azure VM power state is left unknown. These scopes appear in the JSON;
unconfigured scopes remain unobserved. Failed requests, malformed identities,
pagination errors and resource limits fail the report. The command makes no
cloud changes or journal writes. It requires disk/address read permissions in
addition to those used for runner selection. Collection spans the reported
start/end times rather than an atomic cloud snapshot.

This command supplies observations for monitoring. It does not identify or
delete orphans, save a baseline, schedule comparisons or deliver alarms.
The versioned report brackets cloud reads with journal-owned allocation snapshots
and dispatch-history fingerprints. Those snapshots contain only projected native
scope/path/incarnation, allocation ID and creation time. Private binding/provider
JSON and arbitrary dependency maps are excluded. Operators consume this API rather
than reading the journal's private schema.

Administrators can add a dated absolute component price under central
`effective_prices`. Copy the complete `financial_price_scope` object from a
live Explain result into the record as TOML fields under
`[effective_prices.scope]`; convert its nested objects into nested TOML tables
as shown below. Optional fields absent from the report must stay absent.
Each component rate is the USD hourly total for that exact
component and product, including the configured disk size where the component
is `disk`. Quote the decimal rate so parsing never passes through binary
floating point. `source` and `reference` are bounded, administrator-supplied
nonsecret evidence labels shown in Explain. `observed_at_unix_seconds` is when
the evidence was originally observed, and `valid_from_unix_seconds` /
`valid_until_unix_seconds` define a half-open interval.

An active exact override is invalid when its component is already marked
`included_in_compute` by the qualified cloud quote. This is a central
configuration error: Explain and Create reject the analysis even when other
cloud offers remain available. Remove or correct the record before retrying.
The adapter's included-charge flag and quote obligations remain authoritative.
Some adapters, including GCP, reject incomplete quotes before returning them;
an effective price cannot supply facts hidden by that adapter-level validation.

original age and can make the quote ineligible under the configured policy.

## Daemon ownership and recovery

Run one daemon for one local SQLite database. It holds an exclusive process
lock and recovers durable operations at startup. Keep the database on durable
local storage; shared-filesystem or multi-process ownership is unsupported.
Retain the exact child executable, provider configuration, credentials, and
digests for every nonterminal allocation. Back them up with the database.
Active pools retain their full frozen provider configuration. A drained pool's
configuration remains required only while an allocation may still own a
dispatched resource. Deleted allocations retain their pins and audit history in
the journal but do not require their old provider files or credentials at
startup.

During pool drain, Outrider removes failed, unregistered GARM records only when
the matching allocation is deleted and tombstoned, has no dispatch or child
attempts, and retains no provider result or native identity. Controller, pool,
snapshot and runner identities must match. The GARM record must still report
`error`/`pending`, with no provider ID, registered agent, addresses or job. It is
read again before deletion; the pool remains owned until GARM reports it empty.
Unknown records, including failures before allocation reservation, require
operator reconciliation. This cleanup does not infer cloud absence or delete
resources that may have reached a provider.

The provider wrapper reports the fixed concurrency-limit and closed-admission
reasons alongside their HTTP status. Other failed daemon responses retain only
the HTTP status; arbitrary response text is not copied into GARM logs.

After a create may have reached a provider, timeout, error, or restart does not
prove no VM exists. Outrider fences duplicate creates and reconciles with
provider observations and journaled ownership. A failed List call, empty
filtered result, or expired TTL does not prove a late create is absent. Do not
reuse a reserved runner name while its operation is unresolved. Escalate with
the retained controller, pool, cloud scope, request name, and child evidence.

A successful child return can precede native inventory visibility. Outrider
repeats empty ownership lookups every two seconds for at most thirty seconds,
within the original allocation deadline. It dispatches no additional create;
lookup errors fail immediately and cancellation retains the cleanup fence.
Unresolved handoffs report returned owned-inventory/same-name counts and a
redacted rejection category. Adapter ownership filters still apply to those
counts; they do not describe foreign resources hidden by the adapter.

Azure ownership inventory requests full VM models. The `statusOnly=true`
projection can omit tags required to establish ownership, as reproduced in
[Azure's API specification issue](https://github.com/Azure/azure-rest-api-specs/issues/42411).
Full inventory may omit runtime state; inspect the retained VM identity when
runtime state is required. Missing ownership tags never count as ownership.

Unresolved cleanup remains owned and counts against allocation limits while
Outrider retries it with exponential delays from one second up to five minutes.
The journal retains one logical Delete action and its first intent time across
restarts. Retry exhaustion, elapsed time, and empty inventory do not release
the tombstone; cleanup needs positive ownership evidence and a verified delete.

### Operator-attested cleanup resolution

When the provider cannot return a terminal operation ID, an administrator may
resolve one cleanup tombstone after independently proving that all submitted
cloud operations are terminal, no local provider process can submit more work,
and every scoped resource and dependency is absent. An empty provider inventory
alone is insufficient. This command records an administrator attestation; it
does not query a provider or decide that absence is safe.

Stop the Outrider daemon before both inspection and resolution. Each command
opens the existing SQLite journal and takes its exclusive process lock. It
may apply a normal local schema migration before inspection. It does not load
provider credentials, execute a provider child, or call a cloud, GARM, or
GitHub API. Cleanup commands require a Unix host with the provider's
process-group support. A missing or mistyped database path is rejected rather
than initialized as an empty journal.

Inspect exactly one allocation and save the JSON output:

```sh
outrider cleanup inspect \
  --database /var/lib/outrider/journal.sqlite \
  --controller garm-prod \
  --allocation alloc-opaque-id > cleanup-inspection.json
```

The output contains retained resource scope, provider pin hashes and revisions,
the selected image alias and native image ID, and safe network placement IDs
from the retained catalog. It also includes native resource/dependency IDs
when known, cleanup timing, and a canonical scope digest. It does not print
retained configuration, credential paths, environment values, child stderr,
or bootstrap/token material. For opaque
creates without a native identity, the reserved name and retained provider
scope define the operation boundary; no empty inventory is treated as proof.
The digest also binds dispatch/return history, cleanup action attempts, and
unresolved lifecycle action identities. Any later retry or positive evidence
requires a new inspection and invalidates the earlier attestation.

After the evidence review, create a UTF-8 JSON attestation. The evidence
reference is a nonsecret ticket or evidence identifier using letters, numbers,
and `._:/#-` only. It must not be an absolute path. `verified_at_unix_seconds`
is the time the independent absence proof was checked; it must be current
(within one hour) and no earlier than the latest dispatch, return, or cleanup
attempt recorded in the inspection.

```json
{
  "schema_version": 1,
  "allocation_id": "alloc-opaque-id",
  "controller_id": "garm-prod",
  "pool_id": "pool-123",
  "runner_name": "outrider-abc123",
  "scope_digest": "COPY_FROM_INSPECTION",
  "evidence_reference": "change:INC-482#evidence-7",
  "verified_at_unix_seconds": 1792699200,
  "acknowledgements": {
    "all_cloud_operations_terminal": true,
    "no_local_provider_process_can_submit_work": true,
    "all_resources_and_dependencies_proved_absent": true
  }
}
```

Resolve using the same journal:

```sh
outrider cleanup resolve \
  --database /var/lib/outrider/journal.sqlite \
  --attestation cleanup-attestation.json
```

Resolution accepts only the exact tombstoned, dispatched `deleting` allocation
whose scope still matches the inspection. The audit row records the canonical
attestation digest, evidence reference, verification and commit times, and the
effective OS UID/GID. Audit and terminal state commit in one transaction.
Repeating the identical attestation is idempotent. The allocation and name
fences, provider pins, native identity, first delete intent, and operation
history remain retained; only active allocation-cap accounting is released.
Normal pool drain may then continue.

If you inspect that allocation later, the CLI returns the saved pre-resolution
inspection with `historical_audit: true`. This preserves the original evidence
for review; it is not a fresh inspection for another resolution.

Mis-attestation can leave a cloud resource behind. A late child Create result
cannot reopen a resolved allocation, and a duplicate Create remains fenced by
its retained name. Confirm cloud operations and local provider processes are
terminal before attesting; do not use this workflow to clear uncertainty from
an empty List response.

The stock provider lifecycle APIs mutate by runner name. Outrider checks
read-only identity and ownership before the child call, but that check can race
with the mutation. Reserve allocated names exclusively to this controller
through cleanup. Azure/GCP do not provide atomic native-ID conditional delete
through these interfaces.

## Bounded reruns

Reruns are disabled by default. Enabling them requires a finite central
`reruns.max_per_run` cap and `reruns.actions_write_permission: true`; repository
and job config cannot enable or expand reruns. A GitHub Actions job rerun also
reruns its dependent jobs, so the cap is per workflow run and the workflow
should account for that wider execution. Outrider verifies the failed job,
exact run attempt, assigned runner, and causal interruption evidence before
reserving a rerun. It uses GitHub's exact-job rerun endpoint; eligibility does
not require unrelated jobs or the whole workflow run to be complete. The
per-run cap counts attempts reserved before the POST, including requests GitHub
denies, outcomes that remain unknown, and failures before transmission such as
unavailable credentials or transport setup. It counts durable reservations
rather than only successful reruns.

The documented `201 Created` response records an acknowledged intent. A
documented `403 Forbidden` response records a terminal denied intent, which is
deduplicated and no longer polled after restart. Check the GitHub App's Actions
write permission and repository policy, then handle any desired rerun manually
in GitHub. Outrider does not automatically repeat a denied request. A timeout,
connection loss, or other unexpected response remains uncertain: Outrider keeps
the durable intent and does not send another POST. This preserves the cap and
prevents a lost response from causing duplicate work.

## Logs and change control

Preserve opaque child-provider failures without exposing credentials or raw
provider stderr. When investigating an unresolved operation, retain its command,
binding, request identity, and journal state. Do not replace provider pins or
remove retained files until all allocations using them are terminal.

Dispatched attempts without a verified allocation outcome remain unknown in
policy history across restart, including positive child returns whose native
ownership could not be verified. They do not count as failed creates;
active create-failure policies follow `missing_data` while that coverage remains
unknown within the configured window. Current pinned providers do not report a durable
definitive failed-create outcome that can safely replace this unknown state.

## Journal retries and retention

Failed relay/check requests use persisted exponential retry delays of 1, 2, 4,
8, 16, 32 and at most 60 seconds. Fresh outbox messages remain immediately
eligible; deferred rows do not consume the dispatch batch limit. Restart retains
the deadline. Unknown or obsolete deliveries are not discarded to reduce logs.
The complete pending-outbox inspection still includes deferred intents.
An already deferred forward can take up to 60 seconds after admission reopens
to become due. Deadlines use wall-clock seconds; a backwards clock correction
can extend the wait until the host clock catches up. Keep host time synchronized.

This requires journal schema 16 (one retry deadline column and index). Upgrade
with a fresh verified backup and one fenced controller. Schema-15 binaries
cannot open a schema-16 journal. A binary downgrade requires its own reviewed
recovery procedure; never restore a stale ownership database over live work.

Recovery compacts terminal webhook and outbox headers and bodies after 30 days
from their terminal transition. It keeps delivery IDs and a SHA-256 digest of
length-delimited identity, headers, and body bytes, so exact webhook replays
remain idempotent and changed bytes under the same delivery ID still fail.
Pending and retry work keeps its original bytes. Schema upgrades backfill a
terminal timestamp at migration time because older journals do not record when
those rows became terminal; this gives legacy payloads a fresh 30-day period
from the upgrade. The raw payload cannot be recovered after compaction.

Deleted or rejected pool snapshots can replace their configuration JSON with an
explicit compacted marker after 30 days only when no dispatched, ambiguous,
created, or deleting allocation still needs that snapshot. The original config
digest and snapshot ownership IDs remain. A terminal repeated create is rejected
before its compacted config is parsed. Allocation pins, native identity,
allocation and name fences, run/cancellation barriers, rerun caps, and cleanup
resolution audit rows are permanent safety evidence and are not expired.

Historical retention uses the larger of the configured history window and 90
days. Recovery processes at most 32 rows per table in one pass. Old latency
values are cleared while their original create outcome and timestamp remain for
deduplication; running samples outside the retention range are removed. Per
candidate, catalog, and provider pin, the journal records the latest removed
sample time. Queries whose window reaches before that floor report incomplete
coverage, so expanded windows cannot turn missing measurements into zero or
bridge a removed running-history gap. Create and interruption outcome rows stay
as compact deduplication and original-time evidence. Cleanup attestations and
native/pin evidence remain permanent and are never part of generic pruning.
Schema 15 stores the history floors and payload digests. Schema 14 binaries
reject a schema 15 journal. A query window at or before a removed-measurement
floor reports incomplete coverage. Do not restore an older journal over later
cloud allocations: it can erase ownership, pin, and cap evidence that cleanup
still needs.
